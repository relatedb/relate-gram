# Feature Specification: The Conformance Collection and its Rust Runner

**Feature Branch**: `accept-adr-015`

**Created**: 2026-11-16

**Status**: Draft

**Input**: User description: "implement ADR-015 on the Rust side: the `conformance/` collection and its Rust runner, converted from the existing fixtures, expectations, golden exports and fixer examples."

This specification implements ADR-015 (accepted). It names the sections of ADR-015 that decide each behavior and does not restate them; where they differ, ADR-015 wins. It adds a directory of cases and a test runner, and it changes no behavior of the library or the command. Runners for other languages are out of scope (RFC-005), and so is the semantic layer of ADR-015 section 2.9.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Every rejected file is a case, and the collection reproduces its diagnostics (Priority: P1)

A developer opens `conformance/reject/` and finds one case for each invalid fixture of today's tests: the text under test, the expected errors with code, line, column and byte offset, and a note on why the case exists. Running the Rust runner gives the same verdicts as the position test does today, and the same errors without a database.

**Why this priority**: the rejected cases are the part of the specification that is already file-based, the conversion is mechanical, and they exercise the case form, the byte-exact files, the starting graph and the exhaustive comparison of diagnostics (ADR-015 sections 2.2 and 2.4) end to end.

**Independent Test**: run the runner over `conformance/reject/`; compare the cases with `tests/fixtures/invalid/` and the old position test.

**Acceptance Scenarios**:

1. **Given** each of the 71 invalid fixtures of today, **When** it is converted, **Then** a `reject` case exists with `input.txt` byte-identical to the fixture and the errors of its `.expect` file as `Error` nodes (ADR-015 section 2.2).
2. **Given** a `reject` case, **When** the runner loads its text into the standard starting graph, **Then** the errors reported equal the case's errors, exhaustively, and the starting graph is unchanged afterwards.
3. **Given** the same case, **When** the runner checks the text without a database, **Then** the same errors are reported.
4. **Given** a case whose expected errors differ from what the library reports by a code, a line, a column, an offset, or by one extra or missing diagnostic, **When** the runner runs it, **Then** the case fails and says which part differs.
5. **Given** the invalid-UTF-8 fixture, **When** it is converted, **Then** its text is `input.bin` and its case passes.
6. **Given** a text with a byte order mark or CRLF line endings, **When** it is in the collection, **Then** a checkout does not change those bytes (ADR-015 section 2.2).
7. **Given** the cap on reported errors, **When** a case lists a `total`, **Then** the runner compares it with the total found before the cap (ADR-015 section 2.2).

### User Story 2 - Every valid file is a case with an expected graph (Priority: P1)

A developer opens `conformance/load/` and finds one case for each valid fixture and each reload fixture: the text, the settings, the graph the database holds afterwards written as gram, the warnings and the counts. The expected graph is checked against the database by the comparison of ADR-015 section 2.3, and a malformed expected graph is rejected by the runner.

**Why this priority**: the valid fixtures are where expectations live as code today, and writing them out as gram is the substance of the collection.

**Independent Test**: run the runner over `conformance/load/`; remove a property from one `expected.gram` and see the case fail.

**Acceptance Scenarios**:

1. **Given** each of the 25 valid fixtures and the 4 reload fixtures, **When** they are converted, **Then** a `load` case exists for each, with its settings, `Warning` and `Counts` nodes, and an `expected.gram` that is the graph the database holds after the load; reload cases give the earlier state as `start.cypher` (ADR-015 section 2.2).
2. **Given** a `load` case, **When** the runner loads the text, **Then** the graph read back from the database equals `expected.gram` by the comparison of ADR-015 section 2.3: the same multiset of node lines and of relationship lines, values compared as gram-value canonical text.
3. **Given** an `expected.gram` that uses a path, a forward reference, an annotation, a map, a repeated definition, or a relationship end that is not defined at top level, **When** the runner reads it, **Then** it fails the case with a message that names the rule (ADR-015 section 2.3).
4. **Given** a load with the identity property set, **When** the expected graph is compared, **Then** identifiers stand for that property and no `@id` is expected (ADR-015 section 2.3).
5. **Given** a graph whose elements differ only in an identifier generated by an export, **When** compared after a reload, **Then** they are equal, and an element that differs in a label, a property key or a property value is not equal.
6. **Given** a `Counts` node, **When** the load is run, **Then** exactly the keys it lists are compared and the others are not (ADR-015 section 2.2).
7. **Given** a value of each Relate type that an expected graph can hold (integer, float, string, boolean, list, date, time, local time, datetime, local datetime, duration, point, UUID, float vector), **When** it is loaded and read back, **Then** the database side and the expected side reduce to the same canonical text (ADR-015 section 2.3).

### User Story 3 - Exports are cases, and a reload of an export is checked (Priority: P2)

A developer finds the expected text of exports in files, not in string literals: `exported.txt` beside the case, compared byte for byte, and a load case that also has `exported.txt` checks that the text loads back to an equal graph.

**Why this priority**: it moves the golden strings out of test code, which is what lets another language use them.

**Independent Test**: run the runner over `conformance/export/` and the `load` cases with `exported.txt`; change a byte of one `exported.txt` and see the case fail.

**Acceptance Scenarios**:

1. **Given** each golden export string in the contract tests, **When** it is converted, **Then** an `export` case exists whose `start.cypher` creates the database and whose `exported.txt` is the expected text (ADR-015 sections 2.2 and 2.8).
2. **Given** an `export` case, **When** the runner exports, **Then** the text equals `exported.txt` byte for byte.
3. **Given** an `export` case that must fail, **When** the runner exports, **Then** the multiset of error codes equals the `Error` nodes, whatever the element or key named (ADR-015 section 2.5).
4. **Given** a `load` case with `exported.txt`, **When** the runner exports the loaded database, **Then** the text equals `exported.txt`, and loading that text into an empty database gives a graph equal to the first one (ADR-015 section 2.3).
5. **Given** a database with float vectors, **When** it is exported, **Then** the text is `embedding` values as in spec 005, and integer vectors fail with the expected code.
6. **Given** a case with `transaction: true`, **When** it runs, **Then** the explicit transaction is open before the operation and the refusal code is the one expected (ADR-015 section 2.2).

### User Story 4 - The fixer's examples are cases (Priority: P2)

A developer finds the fixer's inputs and outputs in files: the text, the options, the fixed text, the corrections applied by code with their counts, and the errors that remain with their positions in the fixed text.

**Why this priority**: the fixer is part of the behavior a port may offer (RFC-005), and its examples are literals in test code.

**Independent Test**: run the runner over `conformance/fix/`; change one `Applied` count and see the case fail.

**Acceptance Scenarios**:

1. **Given** each fixer example in `tests/fix.rs` that is not one of the checks left in Rust (ADR-015 section 2.8), **When** it is converted, **Then** a `fix` case exists with `input.txt`, the options as `settings`, `fixed.txt`, `Applied` nodes and `Remaining` nodes.
2. **Given** a `fix` case, **When** the runner runs the fixer, **Then** the output text equals `fixed.txt` byte for byte, the corrections applied equal the `Applied` nodes by code and count, and the errors left equal the `Remaining` nodes by code, line, column and offset.
3. **Given** a fix whose option is not given, **When** the case runs, **Then** the text is left as it was and the remaining errors are as expected.
4. **Given** the `annotate` option, **When** the case runs, **Then** the markers that the fixer writes are part of `fixed.txt`.

---

### User Story 5 - Capabilities, known failures and results (Priority: P2)

A developer runs the collection and gets a results file that says, for every case, whether it passed, failed, was a known failure, or did not apply because the environment lacks a capability. A case that needs the 16-bit vector flag runs when it is set, and a case that needs it absent runs when it is not.

**Why this priority**: it is the mechanism that lets implementations with fewer abilities use the same collection honestly (ADR-015 section 2.6), and the Rust runner is its first user.

**Independent Test**: run the runner with and without the preview flag and compare the two results files.

**Acceptance Scenarios**:

1. **Given** a case whose `requires` lists a capability, **When** the runner starts, **Then** it probes each capability once and reports a case whose requirement is not met as `not-applicable`, without running it.
2. **Given** a requirement written with `!`, **When** the capability is present, **Then** the case is `not-applicable`.
3. **Given** the preview flag set, **When** the runner runs, **Then** the 16-bit cases run and the cases that require its absence are `not-applicable`; with it unset, the reverse; a full run covers both states in two passes.
4. **Given** a declared `capabilities` file that names a capability the probes did not find, **When** the runner starts, **Then** the declaration is refused; one that removes a capability is accepted when it has a reason.
5. **Given** a case listed in `known-failures.gram`, **When** it fails, **Then** it is reported `skipped` with the reason; **When** it passes, **Then** the run fails as an unexpected pass.
6. **Given** a run, **When** it ends, **Then** `conformance-results.gram` has one `Result` node for each case with its `case`, `status` and the collection `version`, readable by `gram lint --strict`.
7. **Given** the operations an implementation offers, **When** a kind implies an operation it does not offer, **Then** its cases are `not-applicable`.

---

### User Story 6 - The collection is checked, and the replaced tests are gone (Priority: P3)

A maintainer changing the collection gets failures for a misspelled capability, a lint error in a case file, a text file whose bytes would be rewritten, a diagnostic code with no case, or a missing version. The tests that the collection replaces are removed, so nothing is checked twice, and the tests that stay in Rust are named.

**Why this priority**: the checks keep the collection honest as it grows, and removing the duplicates makes the move real.

**Independent Test**: introduce each fault and see its check fail; run the whole suite before and after.

**Acceptance Scenarios**:

1. **Given** `case.gram` and `expected.gram` files, **When** the checks run, **Then** `gram lint --strict` passes on every one and the `input.*`, `exported.txt` and `fixed.txt` files are not linted.
2. **Given** a node label or capability name that is not in `conformance/vocabulary.gram`, **When** the checks run, **Then** the collection fails.
3. **Given** `conformance/VERSION` and `conformance/GRAMMAR_VERSION`, **When** the checks run, **Then** both exist and the version has the form of ADR-015 section 2.7.
4. **Given** the diagnostic codes of the library, **When** the checks run, **Then** every code that has a case-able trigger is the code of some case, and the codes without one are listed with a reason (ADR-015 section 2.8).
5. **Given** the tests that the collection replaces (the position test over the invalid fixtures, the golden export strings, the fixer examples that moved, the valid-fixture assertions), **When** the work is done, **Then** they are removed, and the tests listed in ADR-015 section 2.8 as staying in Rust are still there.
6. **Given** `conformance/README.md`, **When** it is read, **Then** it states the case form, the value table of ADR-015 section 2.3, the vocabulary, the capability probes and how to run the collection, and `docs/` and `CLAUDE.md` point at it.

---

### Edge Cases

- A case directory with a file that the kind does not use, a missing required file, or an unknown key in `settings` or `Counts` fails with a message naming the case.
- A text that is itself a valid gram file with a top-level record is under `input.txt`, not parsed by the runner.
- An empty `requires` list is valid; `case.gram` with no `requires` key fails.
- The same identifier in two cases of one kind fails the collection checks.
- A load case with an anonymous element that is not an end of a relationship is written anonymous in `expected.gram` and compared without an `@id`.
- A relationship end that is anonymous in the database cannot be expected and the case is written so that it has an identifier (ADR-015 section 2.3).
- A `Warning` with no position is matched by code alone.
- A pattern-rs reading limit (a fenced tag, an integer above 2^53, a repeated key) found in a case file fails the collection checks, not the runner (ADR-015 section 2.3).
- A runner invoked from a different directory finds the collection by the crate's own manifest path.
- A case that needs a state Cypher cannot create stays a Rust test, and is listed as such.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The collection MUST live in `conformance/` with the layout, file names and kinds of ADR-015 section 2.2, a `VERSION` file starting at 0.1.0 and a `GRAMMAR_VERSION` file (ADR-015 section 2.1).
- **FR-002**: Every invalid fixture MUST become a `reject` case whose text is byte-identical to the fixture and whose errors are those of its `.expect` file; the invalid-UTF-8 fixture MUST be an `input.bin` (ADR-015 section 2.2).
- **FR-003**: Every valid fixture and every reload fixture MUST become a `load` case with `expected.gram`, `Warning` and `Counts` nodes where the load produces them, and `start.cypher` for the reload cases (ADR-015 section 2.2).
- **FR-004**: The golden export strings MUST become `export` cases and the fixer's examples MUST become `fix` cases, except the checks that ADR-015 section 2.8 leaves in Rust, which MUST stay and be named in `conformance/README.md`.
- **FR-005**: The runner MUST read `case.gram` and `expected.gram` with `relateby-gram`, used as a dev-dependency only, and MUST NOT parse `input.*`, `exported.txt` or `fixed.txt` (ADR-015 sections 2.3 and 2.10).
- **FR-006**: The runner MUST enforce the expected-graph rules of ADR-015 section 2.3, and MUST compare graphs by the canonical-line multisets, ignoring generated identifiers, with values reduced through the one value table on both sides.
- **FR-007**: The runner MUST compare diagnostics exhaustively with positions, counts over the keys listed, exported text and fixer output byte for byte, export failures by code, and MUST NOT compare message wording or related positions (ADR-015 sections 2.4 and 2.5).
- **FR-008**: The runner MUST run a `reject` case against the standard starting graph, require it unchanged afterwards, and also check the text without a database (ADR-015 section 2.2).
- **FR-009**: The runner MUST apply the capability probes of ADR-015 section 2.6 at start-up, handle `!` and the two passes of the 16-bit flag, report `not-applicable` without running, treat known failures as ADR-015 section 2.6 says, and write `conformance-results.gram`.
- **FR-010**: `gram lint --strict` MUST pass on every `case.gram` and `expected.gram`; the vocabulary, the version files, unique case identifiers and the coverage of diagnostic codes MUST be checked (ADR-015 section 2.8).
- **FR-011**: `.gitattributes` MUST keep the bytes of `conformance/**/*.txt` and `*.bin` unchanged on checkout (ADR-015 section 2.2).
- **FR-012**: The tests that the collection replaces MUST be removed in the same change, and no behavior of the library or the command may change.
- **FR-013**: `conformance/README.md` MUST document the form, the value table, the vocabulary, the probes and how to run, and `CLAUDE.md` and the project documents MUST point at it.

### Key Entities

- **Case**: a directory of files under `conformance/<kind>/<id>/`: a gram description, the text under test, expected text or graph, and a starting database, as ADR-015 section 2.2 lists.
- **Canonical line**: the text of a node or a relationship that both sides of a graph comparison reduce to (ADR-015 section 2.3).
- **Capability**: a named ability of the environment with a probe, that a case may require or require absent (ADR-015 section 2.6).
- **Result**: one line of `conformance-results.gram` for one case.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All 71 invalid fixtures, 25 valid fixtures and 4 reload fixtures are cases; the runner passes all of them, and a deliberately wrong expectation fails the case it belongs to.
- **SC-002**: Each `export` and `fix` case that replaced a golden string or a fixer example passes with the output compared byte for byte.
- **SC-003**: Run with the preview flag set and unset, the runner's two results files together cover every case, each case `passed`, `skipped` or `not-applicable` in each, and none `failed`.
- **SC-004**: `gram lint --strict` passes on every `case.gram` and `expected.gram`, and the collection checks pass.
- **SC-005**: Every diagnostic code of the library is the code of some case or is listed with a reason.
- **SC-006**: The full suite (`cargo test`, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `scripts/check-public-api.sh`) passes, and the runner's time is recorded in `tasks.md` and stays within twice the time of the tests it replaces.
- **SC-007**: Nothing the collection replaces is checked twice: the removed tests are named in `tasks.md`, and the number of Rust tests that stay is the number ADR-015 section 2.8 describes.

## Assumptions

- `relateby-gram` 0.7.x resolves as a dev-dependency beside `relate`, `tree-sitter` 0.25 and `gram-value` (checked while writing ADR-015); it has not been compiled into this crate yet.
- The `gram` tool (`gram-data`) is available to run `gram lint`, or the linter's library is called from a test; the choice is for the plan.
- The preview flag is a process-wide environment variable, so the two passes are two runs, as the existing 16-bit tests already are.
- The value table of ADR-015 section 2.3 can be written from the existing fixtures; any value type it cannot cover is found while converting and recorded.
- The Rust coverage test that every code has a fixture is replaced by the collection's check (FR-010).
- The first release of the collection is 0.1.0.
